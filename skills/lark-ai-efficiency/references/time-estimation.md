# AI 实际耗时与完整交付链审计

本参考文件是 `lark-ai-efficiency` 阶段 B 的强制规则。目标不是只计算 AI 后台执行时长，而是可靠恢复同一成果的完整端到端人机协作过程。

## 完整交付链识别

阶段 B 深读后，必须先建立交付链，禁止直接按单轮消息或最后一次修改计算 D 列。同一交付链可以跨多个会话、AI 工具和日期；是否合并取决于成果之间的因果关系，而不是会话 ID 或时间间隔。

以下任一证据成立时，优先视为同一交付链：

- 操作同一个项目、Jenkins Job、Skill、脚本、文件集合、功能或最终产物；
- 用户使用“继续”“不完整”“再改一下”“验证一下”“提交并推送”“同步线上”“还是不行”等续作表达；
- 后续修改是在修复、补全、推翻或验证前一次 AI 结果；
- 先经历方案比较或格式探索，再实现、验证和收敛为最终方案；
- 早期失败、回退或被用户否定的尝试，是得到最终交付所经历的实际协作过程。

## 交付链边界

1. **起点**：取最早对最终成果产生实际影响的用户事件，包括问题提出、需求探索、方案选择和首次实现指令；不得从最后一条明确修改指令重新起算。
2. **终点**：取最后一次验证、用户复核后的修正、提交、推送、部署、线上同步或明确完成结果；只完成本地修改但用户继续要求发布时，不得提前结束。
3. **持续迭代**：需求逐步明确、用户认为功能不全、反复验证后继续完善，均属于同一交付链；不得为了得到更短 D 列拆成多个高倍率记录。
4. **失败成本**：错误分析、无效实现、回退和重新实现只要发生在同一交付链中，都计入 D；C 列仍按中高级开发者独立完成最终交付的合理基线估算，不能因 AI 返工同步抬高。
5. **允许拆分**：只有交付物、验收标准和后续用途均独立，且后续工作不依赖前一成果时才能拆分。更换话题、跨天、重开会话或较长间隔本身不足以证明是新工作单元。
6. **跨来源合并**：同一成果先在 Codex 分析、再用 Claude 修改或用其他工具验证时，合并为一个候选。

## 回归用例

- `研究 Jenkins 可预览格式 → 实现 HTML+XLSX → 用户认为功能不完整 → 去掉 XLSX 并限制 Top 10 → 验证并推送`：起点是格式研究，不是最后的“去掉 XLSX”。
- `实际运行 Skill → 发现计时/写入校验问题 → 讨论评估口径 → 修改 Skill → 完成验证`：如果实际运行直接触发优化，应从运行和问题发现开始，不得只统计修改 Markdown 的最后几分钟。
- `先诊断错误 → 修复被用户否定 → 补充产物或日志 → 重新定位 → 验证结论`：失败尝试属于同一交付链；跨夜无事件间隔必须按本文件的自动归因规则切分，不能把整段跨度自动全算或无依据全扣。

## 边界审计输出

每个候选在计算 D 前必须生成本地审计结果：

```text
交付链：需求探索 → 首次实现 → 用户复核 → 功能补全 → 验证/提交
起点：YYYY-MM-DD HH:mm:ss（触发事件摘要）
终点：YYYY-MM-DD HH:mm:ss（完成事件摘要）
跨会话：是/否
待归因间隔：0 段 / N 段，共 X 分钟
自动扣除间隔：0 段 / N 段，共 X 分钟（逐段记录规则与证据）
最终结果后审阅：已覆盖 / 未知 / 用户补充
时间可信度：高 / 中 / 低
```

该结果只用于本地计算和候选预览，绝不写入飞书。

## D 列计算

D 列记录用户与 AI 完成该交付链所占用的端到端时间，包含用户输入、阅读、思考、审阅、确认、审批、人工验证，以及 AI 推理、工具执行、等待外部结果和返工。

默认计入：

- 用户输入、阅读、思考、审阅、确认、审批、人工验证及等待下一轮回复；
- AI 生成、推理、工具执行、工具结果返回和最终输出；
- 用户发现结果不完整后继续思考、验证和提出修正的时间；
- 同一交付链内为最终成果发生的失败尝试、回退和重新实现。

优先扣除可验证的离开时段；对于没有显式前后台事件的长空白，必须继续执行下节“自动间隔归因”，以任务完成/恢复边界、其他主会话活动、工具运行状态和本地时段证据判断。不得仅因间隔长就整段全算或整段全扣。

```text
对话工作秒数 = 完整交付链跨度 - 显式离开时段 - 自动归因空闲/其他任务时段 + 有证据的补充审阅/验证时段
AI实际耗时（H） = round(对话工作秒数 / 3600, 2)
```

- 用户补充的时段按时间区间并集计算，禁止重叠相加；
- 计算和倍率审查使用未四舍五入的秒数，候选展示和写表才四舍五入到 `0.01H`；
- 小于 `0.01H` 时写入 `0.01`，预览同时显示实际分钟数；
- D 较长不能直接抬高 C；C 始终按人工独立完成最终交付的基线估算。

## 自动间隔归因

默认由技能自动完成，不应把每个长间隔转交用户判断。归因过程必须保留在本地候选结构中，至少记录起止、秒数、归因结果、使用规则和支持事件。

### 1. 活动窗口

- 用户消息、AI 消息、推理、工具调用、工具结果、构建/上传进度、`task_started`、`task_complete`、`turn_aborted` 和明确的人工验证事件均属于活动事件。
- 同一候选相邻活动事件间隔不超过 `10` 分钟时合并为一个连续活动窗口。
- `task_complete` 或包含明确交付结果的最终回复后，默认保留最多 `10` 分钟作为阅读与复核缓冲；下一条用户消息前保留最多 `5` 分钟作为输入与思考缓冲。缓冲不得越过其他候选已占用的前台活动窗口，也不得把跨夜空白扩张为工作时间。
- 工具、构建、上传或外部任务有明确开始和结束事件时，按真实运行区间计入；只有“等待中”文字但没有运行事件时，不得把整个无事件空白计入。

### 2. 长间隔自动扣除

连续 `30` 分钟以上没有本候选活动事件时，按以下优先级自动处理：

1. **显式离开证据**：后台、失焦、空闲、休眠、恢复等事件存在时，按事件边界扣除。
2. **完成后恢复**：间隔前为 `task_complete`、明确完成结果或 `turn_aborted`，间隔后为新的 `task_started`、用户续作或“继续/重新打开/可以重新开”等恢复表达，且期间没有仍在运行的工具或外部任务时，保留两端缓冲后，将中段自动归为非工作时间。
3. **其他主任务占用**：间隔内另一个非子代理主会话存在用户、AI 或工具活动时，将对应活动窗口归属给另一个候选，并从当前候选扣除；内部审批、guardian、reviewer 和其他子代理不得被当成独立工作。
4. **跨夜静默**：本地时间 `00:00–08:00` 内没有任何主会话活动，且间隔前后分别有完成/暂停与恢复事件时，该静默区间自动归为非工作时间；区间两端仍按活动窗口缓冲处理。
5. **用户响应延迟**：AI 已给出结论、风险确认或授权问题，用户超过 `30` 分钟后才回复，且期间没有工具运行或验证事件时，只保留完成后的阅读缓冲和回复前的输入缓冲，中段自动扣除。

以下情况禁止自动扣除：

- 日志明确显示构建、上传、部署、数据查询或长任务仍在运行；
- 用户明确表示正在阅读、真机验证、线上检查、审批或等待必须的外部结果；
- 间隔内存在与同一交付直接相关的文件修改、构建产物、提交、发布或验证事件；
- 起止事件缺失，无法判断间隔属于哪个候选。

### 3. 并行任务自动归属

- 同一秒最多计入一个候选，禁止因为多个会话同时有后台事件而重复累计用户协作时间。
- 以最近一次明确用户输入所在的主会话作为前台候选，直到用户切换到另一个主会话；前台候选获得阅读、思考和交互缓冲。
- 后台候选仅保留有明确开始/结束的工具实际运行区间，不再扩张无人事件的等待时间；若后台工具区间与前台活动重叠，重叠秒数只计入前台候选。
- 若用户在一个候选中明确要求后台运行后切换到另一个候选，后台工具的非重叠运行时间仍可计入原候选。
- 只有两个候选存在无法排序的同时用户输入、同一产物被两个来源同时修改，或事件时钟不足以确定前台归属时，才保留为待确认冲突。

### 4. 最终审阅自动判断

- 最终回复包含构建/测试通过、提交推送、发布状态、飞书写入回读或其他可验证结果，且后续没有否定、返工或错误反馈时，自动标记为“已覆盖”。
- 用户在后续消息中继续追问使用方式、查看结果或提出独立新需求，不应把两者之间的空白继续计入原交付。
- 只有最终输出明确要求用户进行尚未记录的真机、视觉、线上或文档验收，且没有后续验证事件时，标记为“未知”。

### 5. 自动归因后的可信度

- 所有长间隔、跨自然日和候选重叠均已按上述规则得到唯一归属，且最终审阅已自动覆盖时，时间可信度可以为高。
- 自动归因完成但仍存在一个无法唯一判定的冲突时，时间可信度为中，只询问该冲突，不得要求用户逐段回忆全部间隔。
- 主要活动窗口、交付边界或事件所属候选无法恢复时，时间可信度为低并建议跳过。

## 待归因间隔与可信度

以下情况必须标记为边界风险：

- 同一交付链连续 `30` 分钟以上没有用户、AI 或工具事件；
- 间隔跨越本地自然日；
- 同一成果跨会话或跨工具继续；
- 最终结果后没有事件，但成果明显需要人工审阅、真机验证、线上检查或文档复核；
- 多个候选时间范围重叠，可能并行处理或重复计时。

风险先触发自动归因，只有归因后仍有冲突才触发确认：

| 时间可信度 | 条件 | 候选处理 |
|------------|------|----------|
| 高 | 交付链清晰；长间隔和重叠已自动或显式归因；最终验证、提交结果或用户复核已覆盖 | 建议录入 |
| 中 | 自动归因后仍存在无法唯一判定的间隔、跨会话冲突、并行重叠或线下审阅 | 需确认 |
| 低 | 起止事件、交付关系或主要时间段无法恢复 | 建议跳过 |

用户不能直接填写 D 总值，但可以纠正自动归因或提供缺失的边界证据；技能不得默认要求用户逐段确认：

- `12:30–13:10 一直在审阅和真机验证`：保留或补充该协作时段；
- `13:10–14:00 已离开电脑`：确认后从跨度中扣除；
- `从第一次做 HTML 预览开始到最后提交都属于同一项`：重新合并交付链；
- 只说“时间不对”且边界不足时，展示自动归因结果与剩余冲突，并只用一个简短问题确认。

高倍率复核和关注标记不能替代时间边界确认；高倍率本身不触发“需确认”。

## D 列提交前检查

任一项为“否”或“未知”，时间可信度不得标为高：

1. 是否搜索过同一项目、文件、Job、Skill 或产物在更早会话中的需求探索和首次实现？
2. 是否包含用户认为“不完整”“不对”“继续优化”后的全部修正和验证？
3. 是否包含失败尝试、回退、重新实现、提交、推送和线上同步？
4. 起点是否早于最后一次明确修改指令，而不是从最后一轮开始？
5. 终点是否覆盖最后一次验证或交付，而不是停在本地修改或等待确认？
6. 所有 `30` 分钟以上、跨自然日和跨会话间隔是否已自动或显式归因，并记录了规则与证据？
7. 最终输出后的人工审阅、真机验证或线上检查是否已覆盖或标记未知？
8. 与其他候选的重叠时间是否已按前台/后台活动窗口唯一归属，避免重复拆分录入？

检查结果必须保存在本地候选结构中，不能只在自然语言中声称“已核对”。用户指出 D 偏短或偏长时，必须展示原边界、遗漏环节和新边界并重算，禁止凭感觉改小时数。
